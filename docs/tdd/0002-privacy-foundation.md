## Approach

ADR-0010 commits the project to **architectural** privacy: type-marked PII, deletion paths, audit logs, encryption-at-rest, voice ephemerality. None of these can be retrofitted cheaply once features have shipped without them, so the foundation lands before any feature that touches personal data.

This design covers three pieces that downstream tasks lean on:

1. A **shared `PII<T>` type marker** that's the same brand everywhere — so a "Discord user ID" carrying the brand in one module is the same un-assignable thing in another.
2. The **`consents` table** that records per-player consent for each defined purpose (starting with voice processing).
3. The **`deletion_log` table** that records, anonymously, what got deleted and when — so an operator can answer "did we honor that erasure request?" without re-introducing the identifying data we deleted.

Encryption-at-rest of PII-marked fields is in scope as a documented mechanism; the implementation lands alongside the first feature that persists a PII field, which is the consents table itself.

### `PII<T>` lives in `packages/core`

Move the existing `PII<T>` brand (currently in `telemetry/src/types.ts`) into a new `packages/core/src/privacy.ts`. Re-export from `@skeinkeeper/core`. Telemetry then depends on `@skeinkeeper/core` and re-exports the brand for backwards compatibility.

```ts
// packages/core/src/privacy.ts
declare const piiBrand: unique symbol;
export type PII<T> = T & { readonly [piiBrand]: true };
export function asPII<T>(value: T): PII<T> {
  return value as PII<T>;
}
export type NoPII<T> =
  T extends PII<unknown>
    ? never
    : T extends ReadonlyArray<infer U>
      ? ReadonlyArray<NoPII<U>>
      : T extends object
        ? { [K in keyof T]: NoPII<T[K]> }
        : T;
```

Rationale for `@skeinkeeper/core`: the brand is a primitive cross-cutting type — it belongs in the foundational package, not in any feature module.

### `server/` package owns the local data store

A new `server/` workspace package holds:

- The Drizzle schema (TypeScript) for every persistent table.
- The migrations directory (`server/drizzle/`) generated by `drizzle-kit generate`.
- The data-access layer the rest of the codebase calls into. (Per ADR-0008, the tenant-aware query builder lives here; the full implementation lands in Phase 1.1.)

Why Drizzle over Prisma / Kysely / raw SQL:

- Schema-as-code in TypeScript, no separate schema DSL to learn.
- Generates SQL migrations deterministically; we commit them.
- First-class SQLite and Postgres support, so multi-campaign-group deployments can move dialects without rewriting.
- Light runtime; no codegen step in the hot path.

Why `better-sqlite3` as the driver: synchronous (which matches the in-process embedded-database use case), fast, the most-used SQLite driver in the Node ecosystem, prebuilt binaries available for all common platforms.

## Components & interfaces

### Schema: `consents`

```ts
export const consents = sqliteTable(
  "consents",
  {
    id: integer("id").primaryKey({ autoIncrement: true }),
    tenantId: text("tenant_id").notNull(),
    subjectId: text("subject_id").notNull(), // PII — Discord user ID
    purpose: text("purpose").notNull(), // enum: see PURPOSES
    consentTextVersion: text("consent_text_version").notNull(),
    action: text("action").notNull(), // enum: "granted" | "withdrawn"
    timestamp: integer("timestamp").notNull(), // unix epoch ms
    metadata: text("metadata"), // JSON string, optional
  },
  (t) => ({
    bySubject: index("consents_tenant_subject").on(t.tenantId, t.subjectId),
  }),
);

export const PURPOSES = ["voice_processing"] as const;
export type Purpose = (typeof PURPOSES)[number];
export const ACTIONS = ["granted", "withdrawn"] as const;
export type Action = (typeof ACTIONS)[number];
```

The `subject_id` column carries Discord user IDs. At the application layer this column reads back as `PII<string>` — code that handles it must explicitly accept the brand.

Future purposes (e.g., `episodic_memory_retention`, `crash_reporting`) extend `PURPOSES`. Versioning the consent text in the row makes it possible to prove what a player saw when they consented.

### Schema: `deletion_log`

```ts
export const deletionLog = sqliteTable(
  "deletion_log",
  {
    id: integer("id").primaryKey({ autoIncrement: true }),
    tenantId: text("tenant_id").notNull(),
    scope: text("scope").notNull(), // enum: "player" | "campaign" | "tenant"
    subjectIdHash: text("subject_id_hash").notNull(), // SHA-256(subject_id), non-reversible
    adapterName: text("adapter_name").notNull(),
    recordsDeleted: integer("records_deleted").notNull(),
    timestamp: integer("timestamp").notNull(),
    reason: text("reason"),
  },
  (t) => ({
    byTime: index("deletion_log_tenant_time").on(t.tenantId, t.timestamp),
  }),
);
```

`subject_id_hash` is intentionally a one-way hash: the table answers "did we delete the records for {subject}?" by re-hashing the queried subject and matching, but the table on its own contains no recoverable PII. That makes the deletion log itself safe to retain indefinitely for audit purposes — even after the underlying subject is gone.

`adapter_name` records which `DeletionAdapter` performed the deletion (e.g., `"warm_state"`, `"vector_store"`). One row per adapter per erasure event, so a full per-player erasure produces N rows (one per registered adapter).

## Data & state

### Encryption-at-rest

> The per-column encryption approach below is recorded as [ADR-0019](../adr/0019-per-column-pii-encryption.md); this TDD retains its design and rationale.

The implementation is deferred to Phase 0.7 (which adds the first read/write path against the consents table). The mechanism, decided here:

- **Per-column AEAD encryption** (XSalsa20-Poly1305 via libsodium-bindings) for PII-marked columns. The data-access layer wraps reads/writes through `encryptedColumn(name)` helpers that handle nonce generation, ciphertext storage, and decrypt-on-read.
- The encryption key is sourced from the OS keyring (libsecret on Linux, Keychain on macOS, Credential Manager on Windows) and never written to disk in plaintext. Per ADR-0010.
- Per-column rather than whole-DB (SQLCipher) because (a) only some columns need it and (b) it lets the audit and deletion paths work without the key — the data-access layer reads the encrypted ciphertext for deletion purposes; only feature code that reads the plaintext needs the key.

The doc lands now so contributors know the contract. The shim lands with the consents writer in Phase 0.7.

## Dependencies considered

- **Chosen:** Drizzle ORM + `better-sqlite3` — schema-as-TypeScript, deterministic migration codegen, synchronous driver suited to in-process embedded SQLite; OSS, self-hostable, no external service.
- **Prisma** — rejected for alpha: codegen step adds contributor friction and runtime cost is higher; Drizzle gives the same type-safety without build-time complexity.
- **Kysely / raw SQL** — evaluated; Drizzle preferred for its schema-as-code migration generation.
- **SQLCipher (whole-DB encryption)** — rejected as primary mechanism: the audit/deletion code paths often want to read encrypted-PII columns without needing the plaintext (just to verify the row was deleted). Per-column encryption lets that work; whole-DB encryption forces every read through the key.
- **libsodium-bindings (XSalsa20-Poly1305)** — chosen for per-column AEAD: widely-used, audited, OSS, native Node bindings available.

## Alternatives considered

- **Keep PII<T> in telemetry.** Rejected: telemetry isn't the conceptual home of a fundamental privacy primitive; it should be a _consumer_ of the brand, not its owner.
- **Use Prisma instead of Drizzle.** Rejected for alpha: Prisma's codegen step adds friction for contributors and the runtime cost is higher; Drizzle gives us the same type-safety without the build-time complexity. Either could work; Drizzle is the simpler default.
- **SQLCipher (whole-DB encryption).** Rejected as primary: the audit/deletion code paths often want to read encrypted-PII columns _without_ needing the plaintext (just to verify the row was deleted). Per-column encryption lets that work; whole-DB encryption forces every read through the key.
- **Skip the deletion log and trust the operator to remember.** Rejected: ADR-0010's "operator can answer 'what happened in our session'" commitment includes deletions. Without a log, the answer to "did we honor that erasure request?" is unverifiable.

## Telemetry implications

None directly. The consents table is operator-local audit data; nothing leaves the machine. If telemetry is later enabled, the `error.captured` event might fire if a deletion adapter throws, but the registry already covers that case.

## Privacy implications

- **Lawful basis:** consent for the consents table, legitimate interest (audit) for the deletion log. Both are operator-controlled.
- **PII handling:** `subject_id` in `consents` is `PII<string>` at the type level. The deletion log carries no PII.
- **Deletion path:** the `consents` table participates in player erasure (cascades when the subject is deleted). The deletion log entries themselves are _not_ deleted on player erasure — they're the anonymous audit trail proving the deletion happened. Per ADR-0010, that's the intended distinction.
- **Consent:** existence of the table doesn't itself require consent; writing a row IS the consent record.

## Eval implications

None — mechanical infrastructure with unit tests.

## Open questions

- **Key rotation.** The encryption key from the OS keyring needs a rotation story. Defer to v0.5; alpha runs with a fixed key.
- **Hash salt.** The `subject_id_hash` should be salted to prevent cross-installation correlation if multiple operators' deletion logs were ever combined. Per-installation salt stored alongside the keyring entry; details in the Phase 0.7 implementation.
